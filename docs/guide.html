LFG commands and getting started

LFG takes an idea or a Linear issue to a reviewed, tested and security-checked change, with the commit message and pull request description written for you. It runs inside Claude Code as slash commands, backed by the lfg command-line tool. LFG never pushes or deploys, and commits only when you ask and approve it — publishing is always yours.

Requirements

/grill interviews you until goals, users, acceptance criteria and non-goals are clear.

Design and planning

/plan produces a design, ADRs and test-first tickets with dependencies.

Implementation

/build implements tickets test-first, in parallel git worktrees when there are several.

Verification

/check fixes lint, type-checks, runs tests and the build, and replays CI locally.

Security

/secure vets anything new; /pentest runs an offline attack with a local model.

Review

/expert reviews standards, spec and blast radius, returning approve, changes or block.

Release readiness

/ship smoke-tests a Docker image, removes it, and writes the commit and PR text.

Knowledge graphs

code-review-graph and graphify map the repository and stay in sync before every skill.

Team and personal memory

Decisions go to dev-graph, personal notes to second-brain; both run locally.

First-time setup

From a new Mac to your first completed change.

Performed by LFG Automatic Requires you
  1. 1

    Run the installer

    LFG

    It looks at your machine first (read-only), prints exactly what it would change, and changes nothing until you say yes. Core installs only what every LFG repo needs (uv, gh, code-review-graph, graphify), copies LFG to ~/.lfg, puts lfg on your PATH and registers the plugin with Claude Code, turned off. Your Claude Code settings, hooks, skills, MCP servers and CLAUDE.md are left alone. Every change outside ~/.lfg is recorded, and lfg uninstall undoes it.

    git clone https://github.com/varun-singhh/lfg.git && ./lfg/install.sh
  2. 2

    Turn LFG on in a repository

    You

    LFG only works in repos you turn it on for. Everywhere else Claude Code behaves as if LFG weren't installed. You can also do this from lfg ui → Settings → Claude Code.

    cd your-repo && lfg enable
  3. 3

    Add the packs you want

    You

    Optional features install their tools only when you ask: security (scanners for /lfg:secure), shipcheck (Docker), pentest (Ollama, Strix, LuLu), knowledge (dev-graph, second-brain), linear and headroom. Add them from the dashboard or the terminal, then check everything with lfg doctor.

    lfg add security
lfg doctor
    • Run gh auth login if the doctor reports GitHub is not signed in.
    • With the Pentest pack: open LuLu and approve its system extension.
    • With the Linear pack: run /mcp in Claude Code and sign in to Linear.
  4. 4

    Open Claude Code in that repository

    You

    The session-start hook confirms that LFG is on. LFG's commands are namespaced: type /lfg:wizard, /lfg:which and so on. The short form (/wizard) works when no other skill has that name.

    cd your-repo && claude
  5. 5

    Knowledge graphs are built

    Automatic

    The first skill you run builds the code-review-graph and graphify graphs for the repository (static analysis only, no API cost) into .code-review-graph/ and graphify-out/ in the repo. Both are git-ignored, so they are never committed, and one graph serves every branch and worktree. Afterwards, only changes are synced, including uncommitted edits.

    You never have to manage branches for LFG. When work belongs on another branch, or your checkout holds unrelated changes, the agent creates a worktree on its own next to the repo (<repo>.worktrees/<branch>), works there and tells you where the changes are. It never switches your checkout. Worktrees left clean are removed automatically after a day; any with changes are kept for you to commit.

  6. 6

    Choose how to work

    You

    If you are unsure, run /which and LFG recommends the next command.

    Recommended first
    /wizard <idea>

    Guided run of every stage with plain-language explanations; failures loop through /fix until all gates pass.

    Automated
    /lfg <idea | LIN-123>

    The same pipeline with less commentary. Selects the lane and pauses only at checkpoints.

    Manual
    Individual commands

    /grill, /plan, /build, /check, /secure, /expert, /ship — or a single task such as /fix.

  7. 7

    The pipeline runs

    LFG

    Each stage writes its output to a run folder under ~/.lfg/runs/, so any run can be resumed. LFG pauses at checkpoints for your approval. See How a run works.

  8. 8

    Commit, push and open the pull request

    You

    Review the unstaged diff, then use the generated commit message and PR description.

    git commit -F "$(lfg run path COMMIT_MSG.md)"
git push
gh pr create --body-file "$(lfg run path PR_BODY.md)"
  9. 9

    Follow CI and capture learnings

    LFG

    lfg watch follows the CI run (read-only). After the merge, /learn records learnings, principles and playbooks for future runs.

How a run works

Stages communicate only through files in the run folder, never through chat history. This keeps token usage low and makes every run resumable with /wizard resume or after /handoff.

Figure 1. Pipeline stages and their outputs. Express and Hotfix lanes skip the planning stage.

Lanes

The lane is selected from facts — diff size, graph impact radius and sensitive files — so small changes run fewer stages. Any stage can raise the lane; only you can lower it.

LaneApplies whenPlanningPentestTarget time
ExpressDocs, config, copy or CSS only; small impact; no sensitive files——~15 min
StandardModerate impact in one area; no new dependencyYesQuick, diff only1–2 h
FullWide impact; auth, crypto, PII, payments, migrations or infrastructure; new dependency; a principle or invariant affectedYesStandard or deepSame day
HotfixLinked to an open incident—Quick, diff only< 1 h

/secure runs in every lane whenever something new is introduced — a package, URL, container image, CI action, model or MCP server. A blocking finding raises the lane to Full.

Quality gates

All eight gates must pass in every lane before a change is ready.

#RequirementVerified by
1Build, lint and type-check pass/check, lfg gate
2Tests for every changed node pass; untested changes are flagged/check
3Every acceptance criterion maps to at least one test/check
4No open high or critical pentest findings (Standard and above)/pentest
5Expert verdict is not block; every requested change is resolved or deferred to an issue/expert
6AI changes only: evaluation score at or above baseline; cost per call within budget/build
7No blocking /secure finding in anything new/secure
8Ship check: the Docker image builds, runs, passes the smoke test and is removed; checklist complete/ship, lfg shipcheck

Approval checkpoints

LFG pauses and waits for your decision at these points.

#Decision
1Approve the brief
2Approve the design, tickets and lane
3Resolve a blocking security or pentest finding: fix, replace, or accept with a linked issue
4Resolve an expert-review block
5Review the diff, then commit, push and open the pull request yourself
6Lower a lane (only you can)
7Approve any write to Linear, shown as exact text first

Slash commands

Run these inside Claude Code, in a repo where LFG is on. Each one's full name is /lfg:<name> (for example /lfg:ship); the short names below work when no other skill uses the same name. If you have your own /ship, /health or /learn, type the full name. Most also trigger from plain language, such as “is it green?” for /check. Commands marked Explicit run only when typed.

Full pipeline

CommandDescriptionExample prompts
/wizard <idea | LIN-123 | resume>ExplicitGuided end-to-end run of every stage: grill, plan, build, check, secure, pentest, expert, ship check, ship packet and learn. Pipeline stages

CommandDescriptionExample prompts
/grillInterviews you one question at a time, informed by the code graphs, until goals, users, acceptance criteria and non-goals are clear. Records glossary terms and ADRs outside the repository and writes 01-brief.md.“grill me”, “poke holes in this”
/planProduces a graph-scoped design, spec and tracer-bullet tickets with dependencies, owners and test seams in tasks.json, and suggests a lane. Proposes Linear issues for approval.“plan this”, “make tickets”
/buildImplements tickets test-first. A single ticket runs in the working tree; several run in parallel worktrees and are applied as patches in dependency order. Never commits.“build it”, “do the tickets”
/fixBuilds a pass/fail loop, reproduces the problem, finds the root cause, adds a regression test and fixes it. Uses the Hotfix lane for incidents and records a learning.“it’s broken”, “why is X failing?”
/checkRuns the quality gate: fixes lint without suppressions, type-checks, runs affected and full tests, builds as CI does, replays CI locally and reads GitHub CI status.“is it green?”, “will CI pass?”
/secureChecks everything new — packages, URLs, images, CI actions, models, MCP servers — and security-sensitive code, using local scanners, public vulnerability metadata only, and Cloudflare’s security-audit method for the code review. /secure audit runs Cloudflare’s full audit, only when you ask, after you agree a budget.“is this safe?”, “can I add <package>?”
/pentestExplicitOffline Strix penetration test of the local app with a local Ollama model. Refuses to start unless Ollama, the model, Docker, the sandbox image and an egress firewall are ready. Writes 05-pentest.json.“pentest it”
/expertReviews the change on three axes — standards, spec and blast radius (graph impact, principles, invariants) — and returns approve, changes or block.“review this”, “what could this break?”
/shipRe-runs the gate, runs the Docker ship check and shipping checklist, then writes COMMIT_MSG.md and PR_BODY.md. Never commits, pushes or deploys.“ship it”, “ready for a PR”
/learnRetrospective on a run or a week: dev-graph learnings and principles, repository playbooks, second-brain notes and proposed reviewer-rule changes.“retro”, “what did we learn?”

Role agents

Commands delegate work to eight specialised agents: product-manager, architecture-designer, software-engineer, ai-engineer, qa, security-analyst, expert-review and lane-triage. You do not invoke them directly.

CLI commands

Run lfg in a terminal; repository commands must run inside a git repository. Exit codes: 0 success, 1 a check failed, 2 usage or environment error. Most commands accept --json. Slash commands call these for you; day to day you will mainly use doctor, ui, watch, run path and omnigraph status.

Files and folders

LFG adds only its two git-ignored graph folders to your repositories. Everything else is stored in ~/.lfg (mode 700) on your machine, with a 500 MB limit you can change under Settings → Disk space.

Share with your team

LFG is open source: everyone installs it from the repository, and each person decides which repos it runs in. The plugin's skills and hooks call the lfg CLI, which ships inside the plugin, so install with install.sh rather than adding the plugin alone.

StepCommand
Installgit clone https://github.com/varun-singhh/lfg.git && ./lfg/install.sh
Turn on in a repolfg enable (each person, per repo)
Updatecd lfg && git pull && ./install.sh (your skill and rule edits are kept)
Removelfg uninstall

Nothing personal is shared

Tokens, graphs, runs and settings are created on each machine under ~/.lfg; never share that folder. The full steps, requirements and team settings are in docs/sharing.md and in lfg ui → Help → Share LFG.

Security model

These rules are enforced by the plugin’s hooks, not only requested. lfg doctor --selftest verifies them.

LFG never

Pushes, merges, deploys or writes to GitHub; commits without your approval; reads .env files, keys or credential stores; writes a secret anywhere; pentests anything that is not local; or sends code to a cloud model during a pentest.

You always

Approve briefs, designs and Linear writes; commit and push; and complete anything that needs a password or a system prompt, such as GitHub sign-in, LuLu approval and Linear sign-in.
